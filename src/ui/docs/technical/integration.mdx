# Integration guide — Encryption service

## Architecture

The encryption service is built on **two isolated domains** served by a single server:

| Domain            | Role                                                       | Visibility           |
| ----------------- | ---------------------------------------------------------- | -------------------- |
| `data.encryption` | **Vault** — stores private keys, encrypts and decrypts     | **invisible** iframe |
| `encryption`      | **Interface** — onboarding, backup, restore, documentation | **visible** iframe   |

Suite products talk to these iframes through `postMessage`. Private keys **never leave** the `data.encryption` domain.

### User identity: `suiteUserId`

Each Suite product may have its own internal identifiers. The encryption service uses the **`suiteUserId`** — the `sub` claim from the OIDC identity provider — as the user identifier shared across every product.

<Alert severity="warning" title="Cross-product identifier">
  For the `suiteUserId` to be shared across products, the OIDC identity provider must issue a **public** (non-_pairwise_) `sub`, that is
  `subject_types_supported: ["public"]`: the `sub` is then **the same for a given user** whichever Suite product is calling (Docs, Drive, Fichier,
  Visio). Products must use this `suiteUserId` (and never their internal ID) in every interaction with the encryption service.
</Alert>

### Interface authentication

The encryption interface (`encryption`) handles its own OIDC authentication, **independently of the product**. Products do not pass a token to the interface, they only pass the `suiteUserId`.

When the user opens onboarding or the settings, the flow is:

1. The iframe shows an "Authentication required" screen with a **Continue** button
2. Clicking Continue opens a **new tab** on the Keycloak login page (OIDC client `encryption`)
3. The user authenticates against Keycloak (possibly with a second factor)
4. Once authenticated, the tab sends the token through `window.opener.postMessage()` and closes itself
5. The iframe receives the token and renders the actual interface

<Alert severity="info" title="Why a separate authentication?">
  The iframe cannot perform a classic OIDC redirect (redirects are blocked by the identity provider's CSP, and popups are restricted inside iframes).
  Opening a new tab works around those limitations while preserving the security isolation.
</Alert>

## Security

### Iframe isolation

Each domain runs in its own origin context. The browser guarantees that:

- `data.encryption` has its own IndexedDB, unreachable from the other domains
- Private keys (ideally non-extractable CryptoKey objects) stay inside the vault context
- Communication happens only through `postMessage`, with origin validation

### Security headers

<Alert severity="info" title="Content Security Policy">
  The vault uses the most restrictive CSP possible:<br/>
  `default-src 'none'; script-src 'self'; connect-src 'self'; frame-ancestors <allowed domains>`<br/>
  No style, no image, no font — only the encryption script.
</Alert>

- **SRI (Subresource Integrity)** — the script hash is verified on every load
- **Service Worker** — the vault and the client SDK are cached by a SW, which provides offline operation and automatic updates
- **X-Frame-Options + frame-ancestors** — only allowed products can embed the iframes
- **Runtime origin validation** — every incoming `postMessage` is checked in JavaScript
- **Cross-Origin-Embedder-Policy / Cross-Origin-Opener-Policy** — reinforced origin isolation on the vault, reducing the attack surface for side-channel attacks (Spectre, etc.)

### Browser extensions

<Alert severity="warning" title="Known limitation">
  Browser extensions holding broad permissions (`<all_urls>`, `activeTab`) can potentially read page content, including cross-origin iframes, by injecting content scripts. **No browser mechanism exists** to prevent this: it is an architectural limitation of the extension security model.

We applied every available protection (CSP, COEP, COOP, CORP, SRI, iframe isolation) to raise the technical bar, but those measures do not stop extensions with elevated privileges. Users handling sensitive data must make sure only trusted extensions are installed in their browser. A warning is shown during onboarding and during key restore.

</Alert>

### Storage partitioning (Chrome)

<Alert severity="warning" title="Domain constraint: every product must share the same registrable domain (eTLD+1)">
  Since Chrome 115, storage APIs (IndexedDB, BroadcastChannel, localStorage, etc.) inside third-party iframes are **partitioned by top-level site** (eTLD+1). The vault (`data.encryption`) stores private keys in IndexedDB, so if products live on different registrable domains each product gets **its own partition** with isolated keys.

**Works:** `docs.numerique.gouv.fr` and `drive.numerique.gouv.fr` → same eTLD+1 (`numerique.gouv.fr`) → shared partition → keys reachable from every product.

**Does not work:** `docs.gouv.fr` and `drive.gouv.fr` → different eTLD+1 (`docs.gouv.fr` vs `drive.gouv.fr`) → separate partitions → keys generated from Docs are invisible from Drive.

**Development pitfall:** using `localhost` with different ports (e.g. `:7203` and `:7204`) **hides this problem**, because every port shares the same `localhost` site. To test storage separation properly, use subdomains sharing a common parent in `/etc/hosts` (e.g. `a.product.localhost` and `b.product.localhost`, which share the eTLD+1 `product.localhost`).

</Alert>

<Alert severity="info" title="OIDC communication: window.opener.postMessage()">
  The interface's OIDC authentication uses `window.opener.postMessage()` (and not `BroadcastChannel`) to send the token from the callback tab to the
  iframe. `BroadcastChannel` is also affected by storage partitioning: a `BroadcastChannel` created inside a sandboxed iframe (embedded in
  `docs.numerique.gouv.fr`) cannot receive messages from a top-level tab (on `encryption.numerique.gouv.fr`), because they sit in different
  partitions. `window.opener.postMessage()` uses a direct window reference, which partitioning does not affect.
</Alert>

### Operation separation

| Operation                                                         | Reachable from                            |
| ----------------------------------------------------------------- | ----------------------------------------- |
| `has-keys`, `get-public-key`, `encrypt`, `decrypt`                | Every product (through `data.encryption`) |
| `generate-keys`, `export-backup`, `import-backup`, `destroy-keys` | **Only** `encryption`                     |

A product can **never** generate, export or delete keys. Those sensitive actions always go through the encryption interface (`encryption`).

### Network call and privilege separation

The split between the two domains creates an intentional **privilege separation** for calls to the central server:

| Domain                    | Network calls                                                               | Authentication                     | Access             |
| ------------------------- | --------------------------------------------------------------------------- | ---------------------------------- | ------------------ |
| `data.encryption` (vault) | `GET /api/public-keys` only                                                 | **None** (public endpoint)         | Public key reads   |
| `encryption` (interface)  | `POST /api/public-keys/register/{init,complete}`, `DELETE /api/public-keys` | **OIDC JWT** (client `encryption`) | Writes / deletions |

<Alert severity="info" title="Why this separation?">
  The vault (`data.encryption`) stores the **private keys** in its IndexedDB and holds **no authenticated token**. The interface (`encryption`) holds an OIDC token but has **no access to the private keys** (different domain, IndexedDB isolated by the browser).

**If the vault is compromised**: the attacker reaches the local private keys and could decrypt content, but cannot alter the central server (no token). They can neither register forged public keys, nor delete existing ones, nor start key transfers to another device.

**If the interface is compromised**: the attacker has a token and can alter public keys on the server, but has **no access to the private keys** and therefore **cannot decrypt existing content**.

Compromising both domains at once would be required to both reach the private keys AND manipulate the central server. This separation significantly reduces the attack surface.

</Alert>

<Alert severity="info" title="Why are public keys not behind authentication?">

The `GET /api/public-keys` endpoint is reachable **without a token**. That choice is deliberate:

- Public keys are **public by nature** — they are meant to be shared.
- LaSuite is used by tens of thousands of users. Any authenticated user could fetch everyone else's public keys, so requiring a token would add no real protection.
- Protecting this endpoint would mean propagating an authentication token into the vault (`data.encryption`), which would work against the privilege separation principle for no security benefit.

</Alert>

## Quick integration

### 1. Load the client SDK

The SDK is served from `data.encryption` (the same domain as the vault). It is handled by the same Service Worker: cached automatically, and updated whenever a new version is detected.

<CodeBlock language="html">
{`<!-- Classic script (IIFE, exposes window.EncryptionClient) -->
<script src="https://data.encryption.numerique.gouv.fr/client.js"></script>

<!-- Or as an ES module -->

<script type="module">
  import { VaultClient } from 'https://data.encryption.numerique.gouv.fr/client.mjs';
</script>`}

</CodeBlock>

### 2. TypeScript autocompletion (optional)

The SDK is loaded by URL, so TypeScript does not know its types by default. To get autocompletion and type checking in your IDE, download the declaration file:

<CodeBlock language="bash">
  {`# Download the types into your project
curl -o src/types/encryption-client.d.ts https://data.encryption.numerique.gouv.fr/client.d.ts`}
</CodeBlock>

Then reference it from your code:

<CodeBlock language="typescript">
{`/// <reference path="./types/encryption-client.d.ts" />

// Autocompletion now works:
const encryption = new EncryptionClient.VaultClient({
vaultUrl: '...', // ← your IDE suggests the options
interfaceUrl: '...',
});

const { hasKeys } = await encryption.hasKeys(); // ← return types are known`}

</CodeBlock>

<Alert severity="info" title="Keeping the types up to date">
  When the encryption service is updated, download the `.d.ts` file again to get the latest types. Types are not versioned independently from the SDK,
  they always match the version served by `encryption`.
</Alert>

### 3. Initialize the client

<CodeBlock language="javascript">
{`const encryption = new EncryptionClient.VaultClient({
  vaultUrl: 'https://data.encryption.numerique.gouv.fr',
  interfaceUrl: 'https://encryption.numerique.gouv.fr',
  theme: 'dsfr',   // Cunningham theme name: "default", "dark", "dsfr", "dsfr-dark", "anct", "anct-dark"
  lang: 'fr',      // interface language (optional, auto-detected otherwise)
});

// Creates the invisible vault iframe and waits for it to be ready
await encryption.init();`}

</CodeBlock>

### 4. Authentication

Before using the service, pass the authentication context. The `token` is used by the vault (`data.encryption`) for server operations. The `suiteUserId` is the `sub` claim from the OIDC identity provider, the identifier shared by every Suite product.

<Alert severity="warning" title="suiteUserId ≠ internal ID">
  The `suiteUserId` must be the `sub` of the OIDC JWT, **not** your product's internal identifier. It is what lets the encryption service find a
  user's keys whichever product is calling.
</Alert>

<CodeBlock language="javascript">
  {`encryption.setAuthContext({
  token: jwtToken,       // The user's OIDC JWT (for vault operations)
  suiteUserId: userId,   // "sub" claim of the OIDC JWT — cross-product identifier
});`}
</CodeBlock>

<Alert severity="info" title="The interface authenticates on its own">
  The encryption interface (`encryption`) obtains its own token through a separate OIDC flow (Keycloak client `encryption`). The product does not need
  to pass any token to the interface, only the `suiteUserId`, so the interface can attach the keys to the right user.
</Alert>

### 5. Check for keys and trigger onboarding

<CodeBlock language="javascript">
{`const { hasKeys } = await encryption.hasKeys();

if (!hasKeys) {
// Opens the interface inside a container (your modal, sidebar, etc.)
encryption.openOnboarding(document.getElementById('modal-container'));

encryption.on('onboarding:complete', ({ publicKey }) => {
console.log('Keys generated, public key:', publicKey);
// The public key is already registered server-side by the interface
});
}`}

</CodeBlock>

### 6. Encrypt and decrypt

<CodeBlock language="javascript">
{`// Encrypt content (generates a symmetric key, encrypts, wraps it for each user)
const { encryptedContent, encryptedKeys } = await encryption.encryptWithoutKey(
btoa('Sensitive content'),
{
'suite-user-id-1': publicKey1,  // suiteUserId → public key (ArrayBuffer)
'suite-user-id-2': publicKey2,
}
);

// Decrypt with your own copy of the symmetric key
const { data } = await encryption.decryptWithKey(
encryptedContent,
encryptedKeys['my-suite-user-id']
);
const plaintext = atob(data);

// Re-encrypt with the same key (real-time collaboration, auto-save)
const { encryptedData } = await encryption.encryptWithKey(
btoa('Updated content'),
encryptedKeys['my-suite-user-id']
);

// Share the key with new users
const { encryptedKeys: newKeys } = await encryption.shareKeys(
encryptedKeys['my-suite-user-id'],
{ 'new-user-id': newUserPublicKey }
);`}

</CodeBlock>

### 7. Automatic updates

The vault and the SDK are handled by a Service Worker that caches them and checks `GET /api/version` every 5 minutes. When a new version is detected, the SW updates its cache automatically and silently (no event is emitted).

The cache update is atomic: every bundle is fetched, then written in one go. New bundles take effect on the next natural page reload. Nothing is required on your side.

<Alert severity="info" title="Cache and offline">
  The Service Worker makes sure encryption keeps working even offline. A 1h HTTP cache acts as a safety net when the SW is not supported. The version
  check fails silently on a network error and retries every 5 minutes.
</Alert>

### 8. Cleanup

<CodeBlock language="javascript">
  {`// Remove the iframes, stop the version check, release the resources
encryption.destroy();`}
</CodeBlock>

## SDK API

### Product operations (through the vault)

| Method                                                 | Description                                         | Returns                               |
| ------------------------------------------------------ | --------------------------------------------------- | ------------------------------------- |
| `hasKeys()`                                            | Whether keys exist on this device                   | `{ hasKeys: boolean }`                |
| `getPublicKey()`                                       | Fetch the public key                                | `{ publicKey: ArrayBuffer }`          |
| `encryptWithoutKey(data, userPublicKeys)`              | Encrypt content (generates a new symmetric key)     | `{ encryptedContent, encryptedKeys }` |
| `encryptWithKey(data, encryptedSymmetricKey)`          | Re-encrypt with an existing key (collab, auto-save) | `{ encryptedData: ArrayBuffer }`      |
| `decryptWithKey(encryptedData, encryptedSymmetricKey)` | Decrypt with a provided symmetric key               | `{ data: ArrayBuffer }`               |
| `shareKeys(encryptedSymmetricKey, userPublicKeys)`     | Share the key with other users                      | `{ encryptedKeys: Record }`           |

### Configuration

| Method                    | Description                                                                                           |
| ------------------------- | ----------------------------------------------------------------------------------------------------- |
| `setTheme(theme)`         | Change the interface's Cunningham theme ("default", "dark", "dsfr", "dsfr-dark", "anct", "anct-dark") |
| `setAuthContext(context)` | Pass the JWT (for the vault) and the `suiteUserId` (OIDC `sub` claim)                                 |

### Interface operations (onboarding, backup)

| Method                      | Description                                         |
| --------------------------- | --------------------------------------------------- |
| `openOnboarding(container)` | Open the onboarding interface in the HTML container |
| `openBackup(container)`     | Open the key backup interface                       |
| `openRestore(container)`    | Open the restore interface                          |
| `closeInterface()`          | Close the interface iframe                          |

### Events

| Event                 | Payload         | Description                   |
| --------------------- | --------------- | ----------------------------- |
| `vault:ready`         | —               | The vault is initialized      |
| `onboarding:complete` | `{ publicKey }` | The user completed onboarding |
| `interface:closed`    | —               | The interface was closed      |
| `error`               | `Error`         | An error occurred             |

## Integration checklist for products

To integrate the encryption service, each Suite product must:

1. **Expose the `suiteUserId`** — make the OIDC identity provider's `sub` claim reachable from the product's user API
2. **Use the `suiteUserId` in `setAuthContext`** — **never** pass the product's internal identifier
3. **Index by `suiteUserId`** — use the `suiteUserId` as the key in every encryption-related map (`fetchPublicKeys`, `encryptWithoutKey`, etc.)
4. **Do not pass a token to the interface** — the interface (`encryption`) authenticates on its own through its dedicated OIDC client

### Recommendation: second authentication factor (2FA)

The `encryption` OIDC client should ideally require a **second authentication factor** (2FA). The encryption service protects the user's private keys, so unauthorized access to it is particularly critical.

Depending on its configuration, the OIDC identity provider may or may not enforce 2FA globally. If it does not, configuring it on the `encryption` OIDC client is recommended.

<Alert severity="warning" title="2FA across every Suite product">
  Even when the encryption service requires 2FA, an attacker who compromises access to a Suite product without 2FA (Docs, for instance) can reach the
  **metadata of shared content** (document titles, collaborator lists, etc.), even though the encrypted content stays protected. Enabling 2FA on
  **every Suite product**, not just the encryption service, significantly reduces the attack vectors.
</Alert>

## Emergency access (trusted contacts)

The service lets every user designate a **trusted contact** who can help them recover access to their vault if they lose their recovery phrase and all their devices.

<Alert severity="info" title="No product integration needed">
  The feature is carried entirely by the encryption service and `client.js`: management screens, email notifications, and the automatic prompts (an
  invitation to accept, a recovery request to refuse) that the SDK surfaces by itself through an interface overlay whenever a pending state exists.
  Products have **no code to write**: updating the script is enough.
</Alert>

The instance operator does have to configure the notification emails, which are an essential channel (the objection delay only protects the owner if they are told a recovery was requested):

- **`EMAIL_PRODUCT_URL`**: the product page the email links point to. The links carry neither a token nor a deep route: once signed in, the pending state resurfaces on its own through the SDK.
- **`MAILER_*`**: the SMTP configuration (`MAILER_SMTP_HOST`, `MAILER_SMTP_PORT`, `MAILER_SMTP_USER`, `MAILER_SMTP_PASSWORD`), the optional fallback transport (`MAILER_FALLBACK_SMTP_*`) and `MAILER_DEFAULT_DOMAIN`. With no SMTP host configured, the server logs the emails instead of sending them.

In local development a **maildev** container is provided in `docker-compose.yaml`: the emails sent are readable in a web interface on port **7207** (SMTP on port **7208**), and nothing leaves the machine.

## Server endpoints

| Method   | URL                                  | Auth | Description                                                           |
| -------- | ------------------------------------ | ---- | --------------------------------------------------------------------- |
| `GET`    | `/api/version`                       | No   | Unique build identifier (hash of every bundle)                        |
| `GET`    | `/api/public-keys?user_ids=...`      | No   | Fetch public keys by `suiteUserId`                                    |
| `DELETE` | `/api/public-keys`                   | JWT  | Disable your active public key ("start over")                         |
| `POST`   | `/api/public-keys/register/init`     | JWT  | Registration phase 1: receive an X-Wing challenge to decapsulate      |
| `POST`   | `/api/public-keys/register/complete` | JWT  | Registration phase 2: prove possession of the private key and persist |

<Alert severity="info" title="Error handling">
  Endpoints return error codes (not messages). Your application translates those codes client-side. Example error response: `{"code": "rate_limit_keys", "params": {"max": 10, "days": 30}}`.
</Alert>

<Alert severity="warning" title="Rate limiting">
  Public key creation is limited to **10 per user per 30-day period**. Device transfers are limited to **10 per hour**. Those protections prevent
  abuse.
</Alert>
